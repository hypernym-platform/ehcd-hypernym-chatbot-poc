Chatbot Response-Time Optimization Plan

Performance Plan

Cutting chatbot response time

The EHCD chatbot answers every turn with a minimum of two sequential GPT-4o calls. For plain conversational turns, one of those calls is pure waste. This plan removes it — no infrastructure change — and lists the remaining levers.

01 What we have today

Each query runs through a LangGraph pipeline in tools.py. Three nodes, wired router → tool_executor → answer:

routerGPT-4o · stream=False
→
tool_executorparallel DB · fast
→
answerGPT-4o · streamed
  • router_node — one blocking GPT-4o call with the tool schemas. Decides which tools to run. Because it is stream=False, the caller waits for the entire completion before anything else happens.
  • tool_executor_node — runs all chosen tools in parallel via a ThreadPoolExecutor, each on its own pooled PG connection. Already efficient; not the bottleneck.
  • answer_node — a second GPT-4o call, streamed, using a leaner answer-only prompt for the final HTML reply.

A data query therefore costs 2 sequential model calls (router + answer) with tool execution between them. That split is inherent to the design and worth keeping — you cannot stream a final answer until you know which tools ran.

02 Where the time is wasted

The bug

On a turn that needs no tools — a greeting, a thank-you, general chat — the router call still runs to full completion and produces a complete answer in choice.message.content. That text is then thrown away, and answer_node makes a second full GPT-4o call to regenerate essentially the same reply.

So conversational turns pay for two full model round-trips to deliver one short answer. The second call is the entire response latency doubled for no benefit.

03 The fix — no-tool fast path

When the router returns no tool calls and no tools have run yet (tool_call_count == 0), reuse the text the router already produced: push it to the stream queue and end the graph. Skip answer_node entirely. One call instead of two.

The guard on tool_call_count == 0 matters: after tools run, the loop returns to the router, and that post-tool turn must still flow through answer_node so data answers keep streaming token-by-token. The fast path only fires on genuine conversational turns.

1 · tools.py · router_node — reuse router outputedit
else:
    content = choice.message.content or ""
    # Fast path: pure conversational turn, router already answered.
    if content and state.get("tool_call_count", 0) == 0:
        q = state["chunk_queue"]
        q.put(content)
        q.put(None)            # sentinel: end of stream
        return {"needs_more_tools": False,
                "skip_answer": True,
                "final_response": content}
    # post-tool turn (or empty) → stream via answer_node
    return {"needs_more_tools": False}

The router call is stream=False, so a fast-path reply arrives as one block rather than token-streamed. For short conversational answers that is imperceptible — and still faster than today's two calls. Data answers are untouched and keep streaming.
